# The course knowledge graph (LeanRAG): what was there, what was built, how it is measured (2026-11-11)

The owner's request was "implement the LeanRAG graph". `CLAUDE.md` (Phase 2) ticks 2A-2C and leaves 2D open. This file is what a check of the repository found, what was built on 2026-11-11 and with which decisions, the
protocol the retrieval is measured by (fixed before the test run), the numbers (with their dates and configurations), and what is not built. The model provider changed during the project, so a number here belongs to the
setup written next to it and is not comparable with one from another.

**Result (2026-11-12), in short.** The graph was built from the released Fall 2026 material with DeepSeek (249 units, 1,278 entities, 64 clusters, 11 themes; 364 requests, at most about US$0.18 for the part built on 2026-11-12) and measured, by rules written before each run, on two sets of 20 questions (the second written by a separate session) against the course library's search and the live stand-in. **The graph did not beat BM25 over the same chunks on either set** (13 against 14 of 20 at @3, then 11 against 13), and **the new chunks did not beat the live stand-in** (14 against 14, then 13 against 12). The two defects the first run pointed at were worked on in a second round: the fix for comparison questions (`v2`) is the default engine, as a no-harm adoption and not an improvement (13 and 13 at @3 on the new set; it costs first places, 1 and 2 on the two sets, and gains one at @5 on each); the calibration of the graph signal (`v2cal`) fixed what it was built for and cost the question the graph answers, a trade of equal size, and is not used. The answer by the rules is "no graph": the published artifact (`data/leanrag/current`) serves `bm25`. Nothing is deployed and the switch is off; **no retrieval gain was measured from anything built here**, and both question sets were written by models. The details, the misses and what would be tried next are under "Measurements".

## What it is, what it is not

* It is a **hierarchical graph of the released CS6650 course material**: entities (concepts, techniques, protocols, tools, patterns, assignments) found in the text by a model, each linked to the slide pages it came from (G0); clusters of
  entities (G1); themes that group clusters (G2). A **query engine in plain Python** (`leanrag/graph_query.py`) answers `query_knowledge(question, difficulty, top_k)` from it with **no model call and no embedding call** and returns the slides
  that answer, with their numbers. It sits behind **`TAI_LEANRAG=1`, which is off**.
* It is **not** the paper's dense retrieval. There are no embeddings (none is reachable, see "Decisions"): entities are anchored to a question by BM25 over their names and descriptions, and the clusters are made from TF-IDF vectors reduced by an
  SVD. It does not read a picture (19 of the 309 slides of the Fall 2026 decks have no text), follow a chain of relations further than one step, or understand a question.
* It is **not** 2D (nothing uses the graph for mock-interview questions, the patrol's prerequisite check or misconception confidence), **not deployed**, and **not what students get today**: the live knowledge tool is a BM25 stand-in (below).

## The switch and what it changes

| setting | where | default | meaning |
|---|---|---|---|
| `TAI_LEANRAG` | orchestrator environment | **off** | exactly `1`: if a built graph is at `<data>/leanrag/current` (or at `TAI_LEANRAG_DIR`), the agent containers (text agent and the voice call's tool host: both go through `buildVolumeMounts`) get it read-only at `/workspace/leanrag-graph`. Anything else, or a folder that is not what the build wrote, is no mount (`src/leanrag-graph.ts`; a warning says why when the switch is on). |
| `TAI_LEANRAG_DIR` | orchestrator environment | unset | another graph folder (a real directory, not a link). |
| `LEANRAG_GRAPH_DIR` | **set by the container**, not by hand | unset | `container/agent-runner/src/mcp-servers.ts` gives it to the knowledge server when `/workspace/leanrag-graph/manifest.json` exists; `leanrag/query.py` then answers from the graph. | `LEANRAG_MODE`, `LEANRAG_NOW` | the evaluation | unset | which mode the engine runs (`hybrid`, `entity`, `bm25`) and the clock that decides what a student may read; the manifest's `default_mode` is what is served otherwise. |

**Off changes nothing**: no mount, the knowledge server's environment is deep-equal to before (`leanrag-graph-env.test.ts`), `leanrag/query.py` does not import the new engine (`test_off_switch.py`) and the old formatter's output is byte for byte
what git HEAD produced (`test_mcp_format.py`, golden string). The artifact is mounted into a container, so it holds only what a student may read at the time of the build, and it is JSON (no pickle: a container loads data and never runs it).

## Decisions (2026-11-11) and why

1. **Corpus: the released Fall 2026 material**, the same files the live stand-in is made from (`D:\course-world\deploy\cs6650-pages`, the course world's weekly release): `weeks.json` (which week holds which deck and assignment; unreleased weeks are not read), the decks it names
   (`materials-fall2026/`: 9 decks, 309 pages), `homework.json` (assignments that are visible and unlocked), `syllabus.json`. The 15 PDFs of `materials/` are the **previous** term's and are not read. A build refuses a corpus that holds `REFSOL` or `INSTRUCTOR NOTES` (the words `tai_live.sh` refuses on).
   Previous-semester Piazza posts (student text) are not used.
2. **The unit is a slide with its number.** Slides are grouped three or four at a time for extraction (the model cites the slide numbers, a cited number outside the group is replaced by all of the group's), but the evidence the graph returns is one slide: "slide 12 of the Day 4 deck, week 4".
3. **What the model says is checked, not trusted.** The prompt says "use only the text"; an entity whose name has fewer than half of its words in the text is dropped, a relation needs both ends, and every raw answer is kept in a cache (the audit trail; a run that stops is resumed without paying again).
4. **No embeddings.** The gateway has chat models only (`eval/litellm/config.yaml`: DeepSeek, z.ai, Cerebras), Bedrock is not reachable from the live host, and the BGE-small weights on this PC have no runtime here (nothing with torch is installed) and would need one in the image to embed a question. So: clusters from TF-IDF + SVD (scikit-learn,
   already in the image), anchors from BM25. This is a deviation from the paper and from `CLAUDE.md`, and it is the first thing the measurements can show to be a loss. Not done: BGE-small as a second configuration (not agreed, and it would need packages installed).
5. **JSON, not pickle** (`CLAUDE.md` says NetworkX + pickle). Three files: `manifest.json` (corpus fingerprint, the model the API *returned*, tokens, parameters), `graph.json`, `chunks.jsonl`.
6. **Two channels.** Lecture slides and the assignment / syllabus texts are ranked apart: the texts are long, match many words of any question and, in one list, pushed the right slide out of the first five (seen on the development set). Slides come first; up to two texts follow when they match about as well as the best slide, or first when the question is about an assignment.
7. **Three modes** so that the graph's contribution can be isolated: `bm25` (the slides' words only: the control that has no graph, same chunks and stemmer), `entity` (through the graph only), `hybrid` (both). The stemmer is a port of the course library's (`src/docs/library-search.ts`; 140 words checked against the TypeScript one).
8. **Levels** (`entity`, `cluster`, `theme`) change what accompanies the evidence (the clusters and themes the top entities belong to, and the relations between them), not which slides are returned; `auto` reads comparison and overview words and how many clusters the anchors fall in.
9. **Model calls** (build only): two providers, chosen with `--provider`: `deepseek` (the thin slice of 2026-11-11 was built with it) and `zai` (the owner's instruction of 2026-11-11, after the slice: the rest of the build goes through the z.ai GLM Coding Plan he already has, `glm-5.3-flash` at `https://api.z.ai/api/coding/paas/v4`). Both: JSON mode, temperature 0, thinking off (as the gateway's `deepseek` and `glm` aliases send it), the model id the API returns recorded in the manifest. **Which one built what:** the thin slice and then the whole corpus were both built with `deepseek`; on the evening of 2026-11-11 the owner dropped the z.ai plan for the rest and used his DeepSeek balance, so `zai` is code and tests and was never run.
   The key is the provider's own environment variable (`DEEPSEEK_API_KEY` / `ZAI_API_KEY`, or `LEANRAG_LLM_API_KEY`) or typed hidden at a prompt that names the host; one provider's variable is never offered to the other's host. It is never written, and **never read from a file**: the z.ai key lives only on the course host (the gateway's and Nora's env files), and this build runs on a PC that may not read those.
   Every answer is cached (the units, and the cluster and theme names): the key is asked for only when a request really has to be sent, so a finished build can be rebuilt (`--offline`) and the reviewed build published (`--publish-build`) with no key and nothing sent. The plan's quota is shared with the live TAi and Nora, so the z.ai preset sends **one request at a time**, waits out a rate limit (5, 10, 20, 40 s) and stops at the plan's first used-up limit (z.ai codes 1304, 1308, 1310, 1113) or after five units in a row that got no answer, keeping everything done.
10. **Themes**: `theme_ratio` 6 clusters per theme (the plan's `cluster_size=20` would leave two themes for this corpus); `cluster_size` stays 20 for G1.

## The query engine

`GraphIndex.query(question, difficulty, top_k, mode, now)`: the question becomes stems (stop words dropped, at most 14); BM25 scores every visible chunk (slide title and heading counted twice) and every entity (name three times, description once; a bonus when all stems of the name are in the question); the top 8 entities above a quarter of the best are the **anchors**.
A slide's score is `0.5 x text + 0.4 x entities + 0.1 x neighbours` in `hybrid` (each signal normalised within the channel): the entities that were extracted from it count, and the neighbours (one relation step, three per anchor) a little. At most three slides from one deck. A chunk is visible when its `visible_from` (its week's first day, Pacific time, or an assignment's unlock time) is not later than `now`.
The result keeps the shape `leanrag/mcp_server.py` formats: a text with the concepts, the relations and `### Source Course Materials`, one `**Source: <deck>**` line per document (what `container/agent-runner/src/progress.ts` turns into the page's source chips), the slides under it with `[slide N, week W]`, capped at 7,000 characters. Every number that decides a ranking is in `engine_config()`; the evaluation records its hash.

**Engines (profiles), 2026-11-12.** `profile` (argument, `LEANRAG_PROFILE`, or `DEFAULT_PROFILE`, which is `v2` since the second round: rule R1) picks which of these ranks. **`v1`** is everything above, exactly as it ran on the first test set (config hash `255d88ce18e4b132`, checked: 90 query/mode pairs on the development and first test questions give the recorded ranking again). **`v2`** adds the first of the two fixes the first test run pointed at: a question that asks for a comparison (the patterns of `SPLIT_PATTERNS`: "X differ(s)/different from Y", "difference between X and Y", "X versus Y", "X compare(d) to/with Y", "compare X and Y") is split into its two sides, each side is ranked on its own (with the cap of three slides from one deck applying to each side), and the two lists and the whole question's own list are interleaved, a slide once; a question none of the patterns fits, or whose sides come out the same, is ranked as in v1 (a test pins that v1 and v2 rank non-comparisons identically). **`v2cal`** adds the second: the graph signal is calibrated, each anchor weighing the share of the question's information it holds (its stems' idf over the slides) instead of being normalised by the best anchor, anchors below a quarter of the question dropped unless their whole name is in it, the best anchor that points at a slide counting rather than the sum, and the signals used as they are rather than scaled to their best (weights 0.5 / 0.3 / 0.1). It is not `v2`: see "Measurements".

## How the retrieval is measured (fixed on 2026-11-11, before the test run)

* **Questions.** `eval/leanrag/questions_test.json`: 20 questions, mix fixed before any was written (8 lookup, 5 paraphrase, 4 compare, 3 cross-deck), each with the slides that answer it (`groups`: every group must be hit; compare has one group per concept, cross-deck one per deck) and a few `must_contain` words that `eval/leanrag/check_questions.py` confirms are on every labelled page (it passes: 309 pages read, all labels hold).
  Hash of the frozen set (version 1): `b3cd5cef13778bbde742a8355e2b66fff9f39e51637a56679feed27ffc83b577`. A development set of 10 (`questions_dev.json`, hash `679b98312d0ce1fcf46bdc3fafc82554d04c098daea814c1f3ebf7143b33a471`) on topics that are not the test set's is what the pipeline was debugged on. **The questions were written by the model that built the system, from the slides**, not by the instructor or by students: their wording and labels carry that author's view. The owner or the instructor can replace the file (and bump `version`); the harness records the hash of whatever it ran.
* **Systems**, each answering a ranked list of (deck, pages): `library` (the course library's search, the real `src/docs/library-search.ts`, over the PDFs' per-page text), `standin` (what the live tool answers: the course world's own chunker with PyMuPDF text, then `leanrag/stub_query.py`), `bm25` (our page chunks, our stemmer, no graph: **the control**), `entity` (graph only), `hybrid` (what would be served).
* **Score.** A question passes at k when every group is hit by one of the first k items; the item of the stand-in covers two slides, so it is credited when the expected slide is inside the range and its pages per item are reported. Hit counts at @1, @3, @5, by type, and MRR; counts, not just percentages.
* **Decision rules, written before the test run.** (a) *The graph wins* if, at @3, `hybrid` hits at least **two more** of the 20 questions than `bm25` (same chunks, same stemmer); a tie or a one-question difference means no difference and the simpler system (no graph) is the answer. (b) *The page chunks win* if `bm25` hits at least two more at @3 than `standin`: then most of any gain is chunking and tokenising, which needs no graph and no build. Against `library` and `standin` the numbers are reported without a rule. Nothing is turned on for students on the strength of this alone: the switch stays off until the owner says "deploy".
* **What 20 questions can say.** One question is five points. No significance is claimed; a difference of one question is noise; a small set written by the builder can favour what the builder knows. The parameters of the engine were fixed after looking at the development set only and before the test set was run once.

## Running it

```
# 1. nothing sent, nothing read: the stand-in model, a synthetic graph (writes under data/leanrag/dry-run/)
python -m leanrag.build --pages-dir <pages folder> --dry-run
# 2. one real request on one unit (asks for the key, hidden): checks the key, the model id, the answer's shape
python -m leanrag.build --pages-dir <pages folder> --probe
# 3. the thin slice (a few decks), then the whole corpus (DeepSeek; --price-in/--price-out only print a cost bound)
python -m leanrag.build --pages-dir <pages folder> --slice "Day 4,Day 2,Day3" --price-in 0.30 --price-out 1.20
python -m leanrag.build --pages-dir <pages folder> --price-in 0.30 --price-out 1.20
# 3b. (prepared, never run) the whole corpus through the z.ai coding plan: one request at a time, a quiet hour; the key is typed hidden (it names api.z.ai)
python -m leanrag.build --pages-dir <pages folder> --provider zai --max-calls 600 --max-output-tokens 300000
# 4. no key, nothing sent: rebuild from the caches (same answers, same graph), or publish the build that was reviewed as data/leanrag/current
python -m leanrag.build --pages-dir <pages folder> --provider zai --offline
python -m leanrag.build --publish-build <folder name in data/leanrag/builds>           # a slice, a dry run or a partial build is refused
# the evaluation (nothing sent; the library baseline runs the real TypeScript through tsx)
python eval/leanrag/evaluate.py --questions eval/leanrag/questions_dev.json --pages-dir <pages folder> --graph-dir data/leanrag/current --systems standin,library,bm25,entity,hybrid --library-results <library.json> --nora-dir <course world repo> --profile v1 --out <results.json>
```

Needs numpy, scikit-learn and PyMuPDF for the build (the agent image has all three; the query path needs none of them). `data/` is git-ignored: a graph built there does not travel with a deploy.
