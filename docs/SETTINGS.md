# Settings added in this fork

TAi runs here off AWS: its own box, an Anthropic-compatible gateway (LiteLLM) in front of Cerebras, a web channel instead of
WhatsApp. These are the settings that came with that; the rest of TAi's configuration is unchanged. Orchestrator settings are
environment variables of the orchestrator process; the ones marked `.env` are read from TAi's `.env` at every container spawn and
reach the agent container as secrets.

| Setting | Where | Default | What it does |
| --- | --- | --- | --- |
| `TAI_CHANNELS` | orchestrator | `whatsapp` | Channels to start: `whatsapp`, `web`, or `whatsapp,web`. |
| `TAI_WEB_PORT` | orchestrator | `8099` | Port of the web channel's own HTTP API (listens on 127.0.0.1 only; no authentication: for the host and the tests, never proxied). The student page is a separate listener: `PORTAL.md`. |
| `TAI_WEB_OUTBOX_LOG` | orchestrator | unset | `0`: do not append every message the web channel sends to `store/web-outbox.jsonl`. |
| `TAI_PORTAL_*`, `TAI_GOOGLE_CLIENT_ID` | orchestrator | unset | The student page (socket or loopback port, allowlist, cookie secret, Google client id, origin, base path, proxy trust): table in `PORTAL.md`. |
| `CONTAINER_PREFIX` | orchestrator | `nanoclaw` | Agent containers are named `<prefix>-<folder>-<time>` and the orchestrator removes the stale ones of its own prefix at start. Two orchestrators on one docker daemon (an evaluation and the live one) need different prefixes, and neither may be the other's plus `-` (`nanoclaw`, `nanoclaw-live`): the live deployment uses `tailive`. **Every** container whose name begins with `<prefix>-` is removed at start, so nothing else on the daemon may be named that way (the live gateway is `tai-live-litellm` for this reason: the first start of the live service removed a gateway named `tailive-litellm`). |
| `CONTAINER_NETWORK` | orchestrator | `nanoclaw-net` | The docker network of the agent containers (the gateway must be reachable on it). The live deployment uses `tai-live-net`, so its containers cannot see an evaluation's stand-ins. |
| `TAI_NO_SEEDS` | orchestrator | unset | `1` turns every background job off (what an evaluation run sets). Unset or `0`: the jobs below run unless their own switch says no. `src/seeds.ts`. |
| `TAI_REPLY_RULE` | orchestrator | on | `0`: a student's messages no longer get the `<reply_rule>` (a word budget worked out from what they wrote, `src/reply-shape.ts`) after them, and a closing formula ("let me know if...") is no longer taken off the end of a reply. The persona's own length rules stay. The teaching-team chat never has either. `HUMANNESS.md`. |
| `TAI_SEED_BOOTSTRAP` | orchestrator | on | `0`: no one-time run per new student that puts their Canvas grades into COMPETENCY.md. |
| `TAI_SEED_PATROL` | orchestrator | on | `0`: no weekday-morning run per student that may send them a message (it appears in their chat, and as a notification for a student who turned those on: `NOTIFICATIONS.md`). | `TAI_PATROL_GATE` | orchestrator | `on` | The teaching patrol's gate (`src/patrol-gate.ts`, `PATROL.md`): code decides, before any container, whether a student's patrol needs the model today. `on`: a patrol with nothing new is skipped, written down in `task_run_logs`, and one that runs is told why. `shadow`: decides and logs, and the model runs as before (a week of this shows what the gate would save: `tai_live.sh patrol`). `off`: every patrol runs, as before the gate. |
| `TAI_PATROL_INACTIVE_DAYS` | orchestrator | `5` | A student with no message and no call for this long is a signal (until three weeks, when only the weekly check is left). |
| `TAI_PATROL_FLOOR_DAYS` | orchestrator | `7` | The weekly full check: a student the model has not looked at for this many days gets a run whatever else is true (it covers what code cannot see: GitHub, Piazza, this week's topic, the mock interview). `0`: only a new signal runs the model. |
| `TAI_COMPETENCY_WRITER` | orchestrator | `on` | The student model written by the host (`src/competency-writer.ts`, `STUDENT_MODEL.md`): after each answered exchange of a student's chat a cheap model call extracts what it showed and code records it in COMPETENCY.md, `competency/strategy-log.md` and `competency/interviews.md`. `shadow`: does everything but write (logs, at info level and without a word of the student's, what it would have written). `off`: nothing, no call. A value it does not know is `shadow`, not `on`. It sends the student's message and TAi's answer to the gateway (`TAI_VOICE_LLM_URL`/`TAI_VOICE_LLM_KEY`), to the model the text agent already uses. |
| `TAI_COMPETENCY_MODEL` | orchestrator | the text agent's model | The gateway alias of the extraction call. With no model or no gateway key the writer stays idle and says so once. |
| `TAI_COMPETENCY_DAILY_CAP` | orchestrator | `60` | Model calls of the writer per student per day (one per exchange at most; a restart of the orchestrator starts the count again). Past it the exchanges of that day are not recorded. |
| `TAI_COURSE_STATUS_HOURS` | orchestrator | `6` | The class-wide `groups/global/COURSE_STATUS.md` is rebuilt from Canvas by a script this often (`src/course-status.ts`); `0`: off. What a rebuild changed (a new announcement, file, assignment or module, a deadline that moved or came within 24 hours: `src/course-updates.ts`) goes to the activity list of every student who has a conversation on the page; the first page there is, and a Canvas that could not be read last time, are not news. |

Students are found by the Canvas user id on the allowlist; one who has not opened the page is not told. |
| `TAI_CHOICES` | orchestrator | on | `0`: TAi's options (a `<choices>` block in its words: a quick check or a question with a few ways to answer, `src/choices.ts`) are no longer buttons: they stay in the message as a lettered list, with no answer marked. ## DeepSeek

The gateway has a third model, `deepseek` (`deepseek/deepseek-flash`, DeepSeek's own API at `api.deepseek.com`, pinned there; its V4.1 Flash). Nothing uses it
until it is chosen, and **no fallback chain leads to it**: the students' words would go to a provider in another jurisdiction without anyone having decided
that. Choosing it is a deliberate act, for any of three things: `tai_live.sh model deepseek` (the chats and the scheduled tasks), `tai_live.sh model deepseek
--background` (only the scheduled tasks, the patrol being by far the largest consumer), `tai_live.sh set TAI_VOICE_MODEL=deepseek` and `restart` (voice). The

## GLM: the live model since 2026-11-23

**Since 2026-11-23 06:39:11 UTC, every model setting of the live service that said `deepseek` says `glm`.** `glm` is GLM-5.3-Flash, Zhipu AI's model, called through
z.ai's international API at `https://api.z.ai/api/coding/paas/v4` (the GLM Coding Plan endpoint), with thinking off. The settings it replaced:
- `tai_live.sh model glm` sets every model name in `base.env`: the chats, and the scheduled tasks with the patrol. The student-model and state writers follow
  the chats' model.
- `tai_live.sh set TAI_VOICE_MODEL=glm TAI_VOICE_TALK_MODEL=glm TAI_VOICE_EVAL_MODEL=glm TAI_CHOICES_CHECK_MODELS=glm`, then `restart`.

Why: DeepSeek had answered 402 (an empty balance) to every request since 2026-11-16, so chats, calls and patrols had all failed. The owner chose GLM on 2026-11-23.

The release that went with it is e748905:
- The `glm` alias moved to LiteLLM's `zai/` provider. Under `openai/`, the Anthropic route the text agent uses called a path that the coding endpoint does not have
  (HTTP 404 Not Found). The voice relay's chat completions worked either way.
- `tai_live.sh model glm` refuses unless the running gateway answers for `glm` with a tool round trip, as `model deepseek` does.

No fallback leads to or from `glm`. `deepseek` stays in the gateway, unused: once its balance is topped up, `tai_live.sh model deepseek` and the same four settings
bring it back (its guard refuses while it answers 402). Taking the switch back: `~/tai-live/rollback-pre-glm/ROLLBACK.txt`.

The key is the owner's GLM Coding Plan key (`ZAI_API_KEY`, `gateway.env`). The owner decided on 2026-11-05 that it may serve students (`SECURITY.md`). Nora's voice
uses a copy of the same key, so the two share the plan's quota; a quota used up answers 429, and `tai_live.sh check` names the model.

Measured through the live gateway on 2026-11-23: a tiny answer in 1.4 s, and a tool round trip in 3.1 + 3.2 s. Voice turns were 1.5 to 4 s slower on GLM than on
DeepSeek when that was measured on 2026-11-05 (thinking off).

Verified live right after the switch:
- `check` passed with exit 0.
- `smoke` as the owner, with the real tokens, answered in 87 s with this week's Canvas work, through its tools.
- `smoke ask` with a Go program called `run_go`; the program printed gVisor's kernel, and the answer took 47 s.

**Speed** (measured on 2026-11-23, after the switch). GLM through the Coding Plan is much slower than DeepSeek was.

Voice turns, from the end of the student's turn to TAi's first sound (the service's own "voice turn latency" lines):

|---|---|---|
| DeepSeek (11-04 to 11-15, 1,163 turns) | p50 1.4 s, p90 1.8 s | p50 3.4 s, p90 6.2 s |

The same gateway log, call by call:
- DeepSeek: p50 0.6 to 1.7 s at every prompt size, including 16k to 32k tokens uncached.
- GLM: p50 2 to 3 s for small prompts, 6 s for 8k to 16k, and 9 to 35 s for 16k to 32k.

Where the time goes:
1. **Every call is slower.** A single call takes 1.2 to 3.6 s to its first token, then about 44 tokens a second. Neither prompt size nor caching explains it: a 22,000-token uncached prompt answered in 3 to 4 s, at the OpenAI and the Anthropic endpoint alike, and through the gateway or straight to z.ai alike.
2. **Requests sent at the same time are held back.** Four short requests sent at once (each about 2 s alone) all waited until about 16 s, then finished together.
   - A call makes such overlaps on its own. When the student pauses mid-thought, Deepgram starts a think request, then drops it when they go on (the relay aborts it: the gateway logs it with one output token, and the relay dump does not).
   - In the first smoke call, four such requests overlapped and the answer took 14.2 s to its first token.
   - Several students at once would overlap too.
3. **A text chat also waits for its agent container** before the first model call: 9 to 26 s, as before the switch. The text agent sends about 24,000 tokens every call, and one first call took 35 s.

Not the cause:
- Nora: idle for 24 h, and stopped at 06:57 UTC with no change in the numbers.
- The gateway.
- Thinking: answers had 1 to 100 output tokens.

The agent container writes `competency/interaction-summary.md` itself after every answer (the last 20 exchanges, one line each):
the model did not keep it, which left the persona's "is this student new?" test saying yes for everyone.
